# Vani v1.2.1 — P(-1) sweep, closing addendum

**Date**: 2026-08-20
**Version audited**: 1.2.1 (patch — no API change, toolchain pin unchanged at `6.5.32`)
**Parent audit**: [`2026-08-20-v1.2.0-audit.md`](2026-08-20-v1.2.0-audit.md)
**Kernel baseline**: running kernel `7.1.8-arch1-3`

This is not a new sweep. It is the closing half of the 1.2.0 P(-1) sweep: the seven
code-level items §7 of the parent audit filed as *carried forward*, all now closed. No
new analysis was run, no new findings were sought, and the evidence for each item is the
parent audit's — this document records only what closing them changed.

---

## Why these were not in 1.2.0

They were filed as P2 and left for a later release. Revisiting them against the tree
showed every one was a small, bounded edit with an obvious correct answer, so carrying
them would have been a paperwork exercise rather than a scheduling decision. One of the
seven — four comments still naming the deleted stdlib `audio.cyr` — was not a deliberate
deferral at all but a **miss in 1.2.0's own documentation sweep**, which grepped for the
string `5.8.0` rather than for the filename. That is recorded here rather than quietly
folded in.

### The one with real behaviour attached — #2

The others are guards and comments. This one changes what a caller sees, and is worth
stating precisely.

`VANI_ERR_DISCONNECTED` has been a public error code since v0.2.0 and was produced by
nothing. The chain was broken in three places at once: `AlsaPcmState` had no entry for
kernel state **8**, `vani_state_from_raw` clamped its accepted range at 7 (so 8 became
`VANI_STATE_UNKNOWN`), and neither transfer path constructed the error.

The consequence was not merely a missing label. `vani_play` / `vani_record` classify the
post-failure state to decide whether to recover; a disconnected device fell through to
the generic branch, so **the retry logic treated a physically absent device as a
transient error** and would re-prepare it. `src/playback.cyr`'s header comment asserted
the negative returns map to "XRUN, suspended, disconnected" — two of three.

Now: the constant exists and is pinned against the kernel value, `vani_state_from_raw`
accepts `[0,8]`, `vani_state_name` reports `DISCONNECTED`, and both transfer paths return
`VANI_ERR_DISCONNECTED` without retrying.

**This is a semantic change on symbols frozen by
[ADR 0002](../adr/0002-freeze-full-vani-surface-at-1.0.md)**, shipped in a patch. The
justification, stated plainly so a future reader can disagree with it: raw state 8
previously mapped to `VANI_STATE_UNKNOWN`, and no consumer can reasonably have depended
on "unknown" as the answer for a state the kernel gives a name to. The alternative —
holding a correctness fix for a minor because the wrong answer was technically frozen —
would preserve the letter of the freeze at the cost of its purpose.

### Range guards — #3 and #4

Both were confirmed by probe in the parent sweep rather than argued from the source.
`_hwp_mask_set_value` with an out-of-range value writes outside the mask and, past
~4576, outside the 608-byte `hwp` struct entirely. `_hwp_interval_set_exact` truncated an
out-of-u32 argument while the device handle cached the untruncated value, so the device
would run at one rate and report another.

Neither is reachable from any in-tree caller — every one passes an enum constant or a
bounded period. They are enforced now because `vani_format_new` stores `alsa_fmt`
unvalidated, which is the seam an out-of-tree caller reaches them through.

### Benchmarks — and a correction to the first reading

Items #3 and #4 add range guards to two directly-benchmarked functions, so this needed
checking. The first check compared 1.2.1's numbers against the **recorded** 1.2.0 row and
appeared to show a regression: `hwp_interval_set_exact` 8 → 10 ns, `hwp_mask_set_value`
19 → 21, `hwp_init_any` 920 → ~1,020.

**That comparison was invalid.** The two rows were measured in different sessions, and
this machine is running roughly 8% slower now than when the 1.2.0 row was taken —
visible in `ring_200ms_playback`, whose code is byte-identical between the two releases
yet reads ~91.6 µs against the recorded 84.8 µs.

Rebuilding the tagged 1.2.0 tree and benching it in the **same session** gives the real
comparison:

| Benchmark | 1.2.0 (same session) | 1.2.1 | Verdict |
|---|---|---|---|
| `hwp_mask_set_value` | 21 ns | 21 ns | no change |
| `hwp_init_any` | 1,030 / 1,031 ns | 1,008-1,042 ns | no change (overlapping) |
| `hwp_interval_set_exact` | 9 ns | 10 ns | +1 ns, at the resolution limit |
| `ring_200ms_playback` | 90,262 / 91,384 ns | 91,557-91,639 ns | unchanged code, confirms the session offset |

The guards cost nothing measurable except possibly 1 ns on one function — and that one is
configuration-time regardless: all three `_hwp_init_any` call sites
(`audio_set_params_fmt`, `audio_query_caps`, `audio_can_set_params`) run at device setup,
and `audio_write` issues no hw_params ioctl at all.

Two things worth carrying forward from this. First, the `bench-history.csv` row for 1.2.1
is the raw measurement and therefore sits ~8% above the 1.2.0 row **on unchanged code** —
cross-row comparisons in that file are only sound within a measurement session, and the
file has no column recording which session a row came from. Second, this is the second
time in two releases that a benchmark delta turned out to be machine drift rather than
code; the 1.2.0 audit reached the same conclusion by a different route (proving the
timed functions were byte-identical). **A same-session A/B against the previous tag
should be the default method**, not the fallback.

`dhvani` unchanged from 1.2.0 — still failing on its own pre-existing `http_body`, still

## What remains after this

Everything left from the parent audit's §7 is structural — it cannot be closed by an
edit of this size. Filed in
[`docs/development/roadmap.md`](../development/roadmap.md) under Open — P2:

- **A seam for the XRUN / suspend / short-write paths.** The largest genuine coverage gap
  in the tree. Those branches cannot be reached by assertions at all; they need real
  hardware or an injectable ioctl seam. A design decision, not more tests.
- **`vani_format_negotiate`** clamps `snd_interval` as if it were continuous and never
  re-refines with the chosen format, so it can return Ok for a format `HW_PARAMS` then
  rejects. Untestable for the same reason — it builds its own `hwp` via
  `audio_query_caps`, which fails closed on any fd a CPU-only test can supply.
- **Coverage for the 22 frozen-but-uncalled public symbols.** ADR 0002 forbids removing
  them, so the output is coverage. 97% reference coverage reached; this is the residue.
- Extending the distlib drift gate to the `.deps` sidecars (low value, self-healing).
- Six mask call sites relying implicitly on `FIRST_MASK == 0` (correct and pinned;
  cosmetic).

**Not vani's to fix**: `dhvani` does not build (pre-existing, `http_body`), still vendors
vani 1.0.0, and its `docs/guides/rt-safety.md` annotates the `vani_play_from_ring` call
site "no alloc" — false until 1.2.0's M-3, true now.

**Still unverified on hardware.** No sound was played during either half of this sweep:
`/dev/snd` is EACCES for this shell (the logind ACL grants `sddm`). Enumeration works
under yukti 2.3.8 and all programs degrade closed, but the last audible confirmation
remains cyrius-doom 0.30.5 (2026-06-29). Several of the defects fixed across 1.2.0 and
1.2.1 sit on paths that only real playback exercises.
