# Vani v1.2.0 — P(-1) Scaffold-Hardening Sweep

**Date**: 2026-08-20
**Version audited**: 1.2.0 (minor — full P(-1) sweep; cyrius pin `6.5.31` → `6.5.32`)
**Kernel baseline**: running kernel `7.1.8-arch1-3`
**Prior audit**: [`2026-08-20-v1.1.4-audit.md`](2026-08-20-v1.1.4-audit.md)
**Scope**: the full P(-1) checklist (roadmap items 0-10) — cleanliness, test sweep,
distlib, bench baseline, external CVE research, internal deep review, security audit,
regression assertions, post-review benches, documentation audit.

---

## Method, and why the numbers below are not the finders' numbers

Five parallel review lenses — CVE research, correctness, memory safety,
refactor/dead-code, test coverage — followed by **adversarial re-verification of every
non-INFO finding by an independent agent instructed to refute it**. 65 raw findings went
in. The verify pass:

| | count |
|---|---|
| Findings submitted for verification | 55 |
| Held as submitted | **5** |
| Re-rated or corrected | **50** |
| → re-rated to MEDIUM | 7 |
| → re-rated to LOW | 24 |
| → re-rated to INFO / withdrawn | 19 |

**Every severity in this document is the post-verification one.** The finders' first
pass produced 12 HIGHs; exactly zero survived at HIGH. That is the pass working as
intended, not a defect in it — the substance held in almost every case while the
severity, mechanism, or reachability narrative did not.

Isolation: the analysis ran against a read-only copy of the tree, with agents explicitly
forbidden from writing to the repository or running any state-mutating git command. This
was a direct response to the 1.1.4 sweep, where an agent ran `git stash` / `git checkout`
in the live repo and reverted a release in progress. No such incident this time.

Toolchain: every measurement was taken under a private `CYRIUS_HOME` pinned to genuine
cycc 6.5.32.

---

## Verdict

**Seven real defects found and fixed**, none of them toolchain-related, several of them
long-standing. The release also carries a refactor, a documentation correction pass, and
a test suite that went from 259 to 775 assertions.

The pin bump is **provably inert on both axes** — the 40 resolved stdlib modules are
byte-identical between 6.5.31 and 6.5.32, and the two compilers emit a byte-identical
`vani_smoke` — so every byte of change in this release is attributable to vani's own
source.

The single most important structural observation: **four of the seven defects were
invisible to the test suite by construction.** The `AlsaHwParam` offset cancelled itself
at every call site; the S24_LE stride error was masked because the two layers that
disagreed were never compared; the scratch leak had no test because
`vani_play_from_ring` had no test at all; the null-handle faults could not be asserted
because asserting them crashes the harness. Reference coverage was **33%** when this
sweep started. That is the finding behind the findings.

## 1. Defects fixed

### M-1 · The negotiated sample format never reached the kernel
**MEDIUM** · `src/device.cyr`, `src/alsa.cyr` · API-contract defect

`vani_configure` / `vani_configure_buffered` passed `vani_format_bit_depth(fmt)` to the
raw layer, which reconstructed a format from the width via `_alsa_format_for_bits`. That
mapping is one-format-per-width, so the caller's explicit `alsa_fmt` — which
`vani_format_new` accepts and stores, and which `format.cyr`'s own comment describes as
encoding "signed-ness + endian" — was silently discarded:

| requested | programmed | audible result |
|---|---|---|
| `U8` | `S8` | signedness flip — large DC offset |
| `S16_BE` | `S16_LE` | byte-order flip — noise |
| `FLOAT_LE` | `S32_LE` | float bits read as int — noise |

3 of 7 supported formats. Anything on the S16_LE default was unaffected, which is why no
consumer reported it.

**Fix**: new public `audio_set_params_fmt(dev, rate, channels, alsa_fmt, period, buffer)`
carries the real body; the two bit-depth entry points became thin wrappers that select
the default format for a width. `vani_configure*` now pass `vani_format_alsa(fmt)`.
**This is the API addition that makes 1.2.0 a minor.**

**Regression**: `test_format_for_bits_is_lossy` pins the lossiness itself, so the
mapping cannot be "simplified" back onto bit depth.

### M-2 · `audio_write_bytes` mis-sized S24_LE frames
**MEDIUM** · `src/alsa.cyr` · out-of-bounds read

`bytes_per_frame` was `channels * (bit_depth / 8)`, giving **3** for S24_LE whose
physical width is **4** — 24 bits of signal in a 32-bit slot. Confirmed independently
against libasound: `snd_pcm_format_physical_width(S24_LE) = 32`,
`snd_pcm_format_size(S24_LE, 2) = 8`.

On a stereo S24_LE stream that made bpf 6 instead of 8, so `num_bytes / bpf` requested
**4/3 as many frames as the caller's buffer holds**, and `audio_write` handed that count
to the kernel with the caller's pointer — the kernel then read ~1.33× the buffer length,
past its end, into the DAC.

vani's own `vani_bytes_per_sample` has returned 4 for S24_LE since v0.2.0 and is pinned
at `tests/tcyr/vani.tcyr:80`. The two layers simply disagreed and nothing compared them.

**Fix**: new `_alsa_phys_bytes_for_bits`, failing closed on an unknown width.
**Regression**: `test_phys_width_agrees_with_format_layer` asserts the two layers agree.

### M-3 · Ring transfers leaked a scratch buffer on every call
**MEDIUM** · `src/playback.cyr`, `src/capture.cyr` · unbounded memory growth

Both `alloc()`d a fresh buffer per call from a bump allocator that never frees
(`lib/alloc.cyr:12` — "Bump allocator: fast, no individual free"). Reproduced
independently by two agents against the real library functions: **~110 MB RSS per 60,000
iterations**, with RSS tracking `alloc_used` roughly 1:1, so committed memory.

The leak rate equals the stream's PCM byte rate exactly — 48 kHz stereo S16_LE is
~691 MB/hour — and is **independent of period size**, because the zero-work early-out
fires before the allocation.

The sharpest detail: dhvani's own `docs/guides/rt-safety.md` annotates the
`vani_play_from_ring` call site **"no alloc"**, and its capture path pre-allocates a
scratch buffer that `vani_record_to_ring` then ignores in favour of its own.

**Fix**: the buffer lives on the `VaniDevice`, grown on demand — one allocation in
steady state. The handle grew 48 → 64 bytes.
**Regression**: `test_device_scratch_is_reused` asserts pointer identity across calls;
reverting to per-call alloc fails 4 assertions.

### M-4 · `vani_play_from_ring` destroyed audio on any short write
**MEDIUM** · `src/playback.cyr` · data loss

It called `vani_ring_read` — which **consumes** — before issuing the write. A short
write or an XRUN therefore dropped the un-written remainder permanently, with no way for
the caller to recover it. vani's own `programs/vanitone.cyr` documents the short-write
contract this violated.

**Fix**: peek → write → consume only what the device accepted, via two new private
helpers `_vani_ring_peek` and `_vani_ring_advance`. On error nothing is consumed, so the
caller keeps its audio and can retry after recovering the device.
**Regression**: four tests covering non-consumption, exact consumption, clamping, and
wrap-around byte order.

### M-5 · Kernel-supplied counts drove unbounded loops and allocations
**MEDIUM** · `src/mixer.cyr` · stack and heap bounds

`vani_mixer_set_volume` and `vani_mixer_set_mute` looped an unvalidated `ELEM_INFO`
count of `store64`s into a **1224-byte stack buffer**, writes starting at +72 in 8-byte
steps — so any count above 144 ran off the end. `set_mute` had no `count == 0` guard
either.

Reachability of an actual overflow on a correct kernel was **disputed between verifiers**
(LOW vs MEDIUM), and one finder's supporting claim — that the kernel's own cap is
compiled out because `CONFIG_SND_CTL_DEBUG` is unset — was challenged as conflating
`snd_ctl_elem_info.owner` with `.count`. The fix does not depend on resolving that:
`integer.value[]` is **128 longs** in the UAPI, so any count above 128 is already outside
the struct vani is filling, whatever the kernel would have accepted. That is the bound
that shipped, and the code comment states only what was verified.

`vani_mixer_list_elements` got the same treatment: `count` bounded by
`VANI_MIXER_MAX_ELEMS` (4096), all three `alloc()`s checked, and **`used` clamped to what
was actually allocated** — the array is sized from the count pass while `used` comes from
the fill pass, and a card's element set can change between the two ioctls.

### L-1 · `vani_record_to_ring` trusted the kernel's frame count
**LOW** · `src/capture.cyr` · defense-in-depth

`snd_xferi.result` was used unclamped as a copy length, so a value above the requested
count made `vani_ring_write` read past the scratch allocation and push adjacent heap into
the caller's audio ring. Requires the kernel to violate the ALSA ABI — hence LOW, down
from the finder's MEDIUM. Clamped to what was requested and sized.

### L-2 · Null device handles faulted instead of erroring
**LOW** · `src/alsa.cyr`, `src/device.cyr` · defense-in-depth

`audio_open_playback` / `audio_open_capture` return **0** on failure. 14 `audio_*` and 7
`vani_*` entry points then dereferenced that handle with no guard, while their siblings
all had one — 6 of 24 `audio_*` guarded, 11 of 17 `vani_*`.

**Reproduced as exit 139 (SIGSEGV)** from the open-then-use sequence printed in
`src/alsa.cyr`'s own header comment; after the fix the same probe exits 0. LOW rather
than HIGH because no shipped consumer is known to reach it — core-profile consumers all
check their open.

**Regression**: two tests that call every guarded entry point with 0. They are
self-proving — remove a guard and the harness faults rather than reporting a failure.

### L-3 · `vani_ring_new` ignored `alloc()`'s 0 sentinel
**LOW** · `src/buffer.cyr` — filed by the 1.1.2 audit, fixed here. Both allocations now
checked, header before payload.

The broader "16 of 16 `alloc()` sites are unchecked" finding was re-scoped on
verification: only **7** return raw pointers whose 0-on-failure contract vani can
actually honour; the rest cannot be fixed from vani. The reachable ones on the transfer
and mixer paths are done.

## 2. Refactor and cleanup

- **`_puti` was byte-identical across six programs** (md5-confirmed) and carried the
  `i64::MIN` defect stdlib fixed at **6.4.69**: `n = 0 - n` is a no-op at `i64::MIN`, so
  the digit loop never runs and only the sign byte prints. All six deleted; **68 call
  sites** now use stdlib `fmt_int`. Verification established there is **no reachable
  failure** — every call site passes small positive values — so this is duplication
  cleanup, not a bug fix, and the CHANGELOG says so.
- **`programs/vanitone.cyr` held the tree's only `break` inside a `while` that declares
  `var`**, a CLAUDE.md hard rule cyrlint cannot see. Rewritten to flag + `continue`.
  Convention hygiene: no miscompilation was ever observed at any pin vani has shipped.
  Worth recording that the first rewrite kept `while (w < frames)` and continued on the
  flag — which spins forever. The shipped version puts the flag in the loop condition,
  and termination was **proved by probe** for full-progress, short-write and
  immediate-stall cases.

### Recommended against, with reasons

The refactor lens examined and **argued against** each of these; recorded so the next
sweep does not re-litigate them:

- Factoring the 17 agnos `#ifdef` seams, the four `val[1224]` mixer preambles, or the
  EPIPE retry blocks in playback/capture.
- Removing the five zero-call-site stdlib includes (`args`, `hashmap`, `io`, `fs`,
  `chrono`) — verified they do not shrink `dist/*.deps`.
- Adopting `io.cyr`'s `xopen` / `file_open` at the three sites cyrlint flags (carried
  from the 1.1.4 audit; all three are inside agnos `#ifdef` arms that never reach
  `sys_open`, and adoption would push `dist/vani-core.deps` from 4 leaves to 6).
- Deleting the seven now-redundant ioctl sub-assertions — they name the drifting field in
  the failure message ("HW_PARAMS=608 (got 352…)"), which the full-equality assertions
  cannot.

### Dead code

Genuinely thin, and that is the honest answer: **zero** unused private `_` helpers, and
22 public symbols with no call site anywhere — all frozen by
[ADR 0002](../adr/0002-freeze-full-vani-surface-at-1.0.md), so none removable. The
actionable output there is test coverage, not deletion, and 1.2.0 took reference
coverage to 97%.

**The closeout procedure itself was broken.** CLAUDE.md's step 3 said "review the
linker's `dead:` lines after smoke build" — but `programs/smoke.cyr` calls nothing except
`sys_write`, so all 108 public symbols appear dead and the step produces no signal. It
has been replaced with the reference cross-scan that works, including the `&fn` fnptr
references a bare `name(` grep misses (which is how `vani_configure_low_latency` looks
dead and is not).

## 3. Test coverage

**259 → 775 assertions.** Reference coverage **33% → 97%** (36/108 → 106/109 functions,
5/8 → 8/8 files).

Every repair ships a regression assertion. The load-bearing ones were **validated with
negative controls** rather than assumed to work — a test that cannot fail is worse than
no test, and this project has been bitten by exactly that (the 1.1.4 sweep found a CI
format gate that had been structurally incapable of passing):

| Negative control | Result | Old suite |
|---|---|---|
| Reintroduce the +2 `AlsaHwParam` offset | 14 fail | 0 |
| Transpose the `HW_PARAMS`/`HW_REFINE` nr byte | 2 fail | **0** |
| Flip `WRITEI` from `_IOW` to `_IOR` | 2 fail | **0** |
| Revert S24_LE stride to `bit_depth / 8` | 2 fail | 0 |
| Revert the scratch buffer to per-call alloc | 4 fail | 0 |

The two zeros in the "old suite" column are the point: the pre-1.2.0 suite asserted ioctl
*size* and *type* bits separately and never the whole 32-bit value, so an nr-byte
transposition or a direction flip passed silently. `HW_PARAMS` and `HW_REFINE` differ
only in the nr byte.

**Corrections established here**: the `AlsaHwParam` enum has **19** members, not the 17
the 1.1.4 audit and the roadmap both claimed; and `AlsaPcmState` is **not** tautologically
tested (that half of the premise was wrong — `AlsaFormat` was, for 6 of 7 members).

## 4. External CVE / 0-day research

**Incremental window: empty, and confirmed empty rather than padded.** NVD 2.0 API for
2026-08-20 → 2026-08-21, keywords ALSA / sound / pcm: zero kernel-audio records. Of 255
CVEs published that day the single "audio" hit is CVE-2026-73220 (CVAT, a web app).

Going deeper — the point of a P(-1) as opposed to a patch sweep — produced no new
exposure:

- **`compat_ioctl` / 32-bit**: no exposure, for two independent structural reasons. This
  angle had never been checked before despite vani issuing raw `syscall(SYS_IOCTL, …)`
  with hardcoded 64-bit struct sizes.
- **ALSA UAPI drift vs mainline**: zero drift across every constant, struct size and
  field offset vani pins. The only change is the additive `SNDRV_CTL_IOCTL_CARD_BYTES`
  ioctl at `'U' 0x02` that the 1.1.4 sweep already flagged as a forward-drift watch item.
- **PulseAudio / PipeWire**: N/A by construction — vani is ioctl-only. Recorded rather
  than skipped, per the roadmap's explicit requirement.
- **Cyrius 6.5.31 → 6.5.32**: zero security-tagged changes, zero advisories, zero NVD
  records.
- **Historical class review**: each major ALSA CVE class (hw_params refine overflow,
  control element type confusion, xfer frame-count arithmetic, UAF on concurrent
  open/close) mapped to the specific vani guard that closes it.

**Correction to the 1.1.4 audit.** Its "19 new in-window Linux kernel audio CVEs" figure
undercounted substantially: the 2026-07-19 → 2026-08-20 window holds ~67 audio-subsystem
records (ALSA 41 + ASoC 25 + soundwire 1), ~60 of them new after excluding the 07-19
batch. **The disposition is unchanged** — none is reachable through vani's ioctl surface
— but the count in that document is wrong and is corrected here rather than left
standing.

## 6. Documentation audit

- **The cyrius stdlib fold-in was described as future work in eleven live locations** —
  README, CLAUDE.md ×4, `src/lib.cyr`, `src/alsa.cyr`, `cyrius.cyml`,
  `docs/architecture/overview.md`, the roadmap, and the plan document itself. It has
  **already completed**: `cyrius/lib/audio.cyr` no longer exists in the toolchain
  snapshot and cyrius bundles vani as `lib/vani.cyr` (currently at 1.1.4). All eleven
  corrected; the plan doc is marked COMPLETED and kept as the historical record.
- **CLAUDE.md inlined the dist sizes** ("76 KB / 106 symbols", "29 KB / 22 symbols") —
  wrong since 1.1.0, and a violation of the file's own core rule that volatile state
  belongs in `state.md`. Replaced with a pointer.
- **CLAUDE.md named `hwp[608]` as vani's largest stack allocation.** That stopped being
  true at 0.3.0 when the mixer landed — `val[1224]` is larger, at four sites.
- **CLAUDE.md's closeout step 3 was unrunnable** (see §2).
- **The ADR index was missing ADR 0002.** Fixed, and ADR 0003 added.
- `programs/vanitone.cyr` was absent from CLAUDE.md's program tree and Quick Start.

## Reproduction

```bash
# pinned toolchain
CH=/path/to/ch6532
ln -sfn ~/.cyrius/versions            $CH/versions
ln -sfn ~/.cyrius/versions/6.5.32/bin $CH/bin
ln -sfn ~/.cyrius/versions/6.5.32/lib $CH/lib
echo 6.5.32 > $CH/current
export CYRIUS_HOME=$CH PATH=$CH/bin:$PATH

rm -rf build lib && cyrius deps
for f in lib/*.cyr; do cmp "$f" "$CYRIUS_HOME/versions/6.5.32/lib/$(basename $f)"; done

cyrius test  tests/tcyr/vani.tcyr        # 775/775
cyrius bench tests/bcyr/vani.bcyr
cyrius distlib && cyrius distlib core
cyrius_api_surface --scope=project       # 109, matches snapshot
for f in src/*.cyr programs/*.cyr tests/tcyr/*.tcyr tests/bcyr/*.bcyr; do
  cyrius lint "$f"; cyrius fmt "$f" --check || echo "needs fmt: $f"
done
for t in "" --aarch64 --agnos; do CYRIUS_DCE=1 cyrius build $t programs/smoke.cyr build/s$t; done

# the null-handle crash this release fixed (pre-1.2.0: exit 139)
printf 'include "src/lib.cyr"\nfn main() { alloc_init(); audio_prepare(audio_open_playback(99,99)); return 0; }\nvar e = main();\nsys_exit(e);\n' > /tmp/p.cyr
cyrius build /tmp/p.cyr /tmp/p && /tmp/p; echo "exit=$?"   # 0
```
