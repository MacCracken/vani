# Vani v1.2.6 — release security pass

**Date**: 2026-09-27 (UTC; the hardware runs cited below were made on 2026-09-26 PDT)
**Version audited**: 1.2.6 (patch — no public API change; pin unchanged at `6.6.2`)
**Parent audit**: [`v1.2.2`](2026-08-20-v1.2.2-audit.md). 1.2.3, 1.2.4 and 1.2.5 shipped
without an audit doc (toolchain and Result-value-form releases), so this pass covers the
whole window since 2026-08-20.
**Kernel baseline**: running kernel `7.2.6-arch2-1`; UAPI headers `linux-api-headers 7.2-1`;
mainline source at `7.3-rc4`

1.2.6 changes one syscall sequence in shipped code: how a PCM node is opened. It also makes
the test suite's exit status a real CI gate, and adds a real-hardware program and FIFO-based
CPU tests. This pass reviews that new surface, re-pins the UAPI, and sweeps the CVE window.

---

## 1. The new syscall surface — `_audio_open_pcm` (`src/alsa.cyr`)

**The defect it closes (availability, MEDIUM, fixed).** Through 1.2.5 both
`audio_open_playback` and `audio_open_capture` opened blocking, and the kernel answers a
blocking open of a busy PCM by sleeping until the holder closes it. Any process with access
to the node — PipeWire and wireplumber hold it routinely — could therefore hang every vani
consumer at startup, indefinitely. Reproduced on hardware: the 1.2.5 open was still asleep
when `timeout 5` killed it; the 1.2.6 open returns 0 in 71 µs. Kernel paths and measurements:
[architecture note 001](../architecture/001-pcm-open-nonblock.md); decision:
[ADR 0005](../adr/0005-nonblocking-pcm-open.md).

**Review of the new sequence** — `open(path, acc | O_NONBLOCK)` → `fcntl(F_GETFL)` →
`fcntl(F_SETFL, flags & ~O_NONBLOCK)`:

| Check | Result |
|-------|--------|
| Input validation | No external data reaches the flags. `path` comes only from `_audio_devpath` (card and device bounded to 0-99, fixed prefix); `acc` is the literal 1 or 0 at the two call sites. |
| Return handling | `open` < 0 → returned. `F_GETFL` < 0 or `F_SETFL` < 0 → the fd is closed and the error returned, so no path leaks a descriptor. Each caller maps any negative to the documented null handle. |
| Fail-closed choice | A descriptor left non-blocking would turn every write into a short write or `-EAGAIN`, which no consumer handles. The helper therefore fails the open rather than hand one back. |
| Semantics preserved | The kernel copies `O_NONBLOCK` for transfers at open and at every PREPARE; the clear precedes the first PREPARE, so WRITEI / READI / DRAIN block as before. Seven cases measured on hardware (note 001). |
| Buffers | None added to `src/`. Largest stack buffer unchanged: `val[1224]` in `src/mixer.cyr`. |
| agnos | Untouched. The helper's agnos arm is unreachable (both callers return first). |
| fcntl constants | `AUDIO_F_GETFL = 3`, `AUDIO_F_SETFL = 4` — prefixed so the vendored core bundle cannot collide with a consumer's `F_GETFL`; pinned by `test_open_flag_literals` and re-checked against the headers in §3. |

**Hardware** (card 1 ALC897 analog, one subdevice, kernel 7.2.6): `vani_busy_open` 16/16
playback checks (busy open 0 in 4-9 µs; a 4×-ring write blocks for 256 ms and returns in full;
DRAIN 85 ms; both again after XRUN → `-EPIPE` → PREPARE). `vani_probe`, `vani_caps`,
`vani_throughput` and `vani_latency_test` pass through the new open. The capture half was not
run: this shell never had an ACL on `pcmC1D0c`. The playback ACL was revoked before the
release build existed, so the runs were made on `src/` that differs from the release only in
one comment (`src/` is byte-identical to commit `6c285b3`).

## 2. Findings in this release's own new code

### M-1 ✅ The test suite could not fail CI (gate integrity, fixed)

`main()` in `tests/tcyr/vani.tcyr` discarded `assert_summary()`'s failure count and returned
0, so through 1.2.5 no failing assertion could turn CI's Test step red. Every regression
assertion shipped for a security fix — the mixer count bounds, the null-handle guards, the
S24_LE stride — was advisory in CI. `main()` now returns 1 on any failure: not the count,
because an exit status is 8 bits and `cyrius test` reads anything above 128 as a signal
(measured: 139 failures report as "killed by signal 11 SIGSEGV", 256 as a pass). Negative
control: with the `F_SETFL` clear removed, the suite reports 2 FAILs and `cyrius test` exits 1.

### L-1 ✅ FIFO tests opened a predictable `/tmp` path even when `mkfifo` failed (fixed)

The two FIFO tests use `/tmp/vani-test-<pid>.fifo`. As first written they asserted on `mkfifo`
and carried on, so a file planted in the window between the stale-path `unlink` and the
`mknod` — a symlink to a device node, say — would have been opened `O_WRONLY|O_NONBLOCK`
(no write, no truncate, but an open of something the test did not create). Test-only, on
dev and CI hosts. Fixed before release: `_test_make_fifo` returns 0 when `mknod` fails and
the tests return without opening anything. `/tmp` is sticky, so once `mknod` succeeds nobody
else can replace the FIFO. Control: with `mknod` forced to fail, both tests fail loudly, the 9
assertions after it do not run (900 total), and the suite exits 1.

### Reviewed, no finding

- `programs/busy_open.cyr` — no external input; holds at most 64 fds; writes only zero frames;
  the capture read is discarded; raw `alarm` (x86_64 #37) / `setitimer` (aarch64 #103) for
  its watchdog.
- CI security pattern scan over `src/` — clean. No `execve` / `fork` / `sys_system`, no
  hardcoded system-path writes, no stack buffer ≥ 64 KB.

## 3. UAPI re-pin

A C program printing every value vani hardcodes was compiled twice:

- against the installed release headers (`linux-api-headers 7.2-1`): **18 ioctl numbers**
  (13 PCM, 5 control) and **14 constants** — 8 struct sizes / offsets, `SNDRV_PCM_STATE_DISCONNECTED`,
  `SNDRV_PCM_HW_PARAM_RATE`, `O_NONBLOCK`, `F_GETFL`, `F_SETFL` — compared mechanically with
  `src/alsa.cyr` + `src/mixer.cyr`: **0 mismatches**;
- against mainline `include/uapi/sound/asound.h` at 7.3-rc4: output **identical**.

The only difference in the ioctl set is the additive `SNDRV_CTL_IOCTL_CARD_BYTES`
(`'U' 0x02`), present in mainline and not yet in the 7.2 release headers — the forward-drift
watch item since 1.1.4. vani does not use it.

## 4. External CVE research — window 2026-08-20 → 2026-09-27

**Source**: NVD 2.0 API, `pubStartDate=2026-08-20`, `pubEndDate=2026-09-27`,
`keywordSearch=ALSA` (50 records) and `keywordSearch=ASoC` (33). **81 unique.**

| Group | Count | Disposition |
|-------|------:|-------------|
| ASoC / SOF / codec drivers | 28 | Platform-driver internals (probe, IRQ, PM, topology). Not reachable through vani's ioctls except control writes — see below. |
| ALSA USB-audio device drivers | 19 | Device-side (URB handling, quirks, MIDI output). Reachable only with that hardware, typically a malicious or broken device; vani cannot mitigate. In scope per the roadmap only when yukti hands vani a USB card. |
| ALSA seq / MIDI / UMP | 10 | vani opens no seq, rawmidi, UMP or hwdep node. Not reachable. |
| ALSA other drivers | 7 | Probe-time checks and card leaks, IRQ / lock init order, HDA firmware at unbind. Not ioctl-reachable. |
| **ALSA core (pcm / core / control)** | **5** | Mapped individually below. |
| media drivers with an ALSA card | 3 | Card teardown and refcount in capture-device drivers — the unbind class, like CVE-2026-90198. |
| alsa-lib | 3 | N/A by construction: vani is ioctl-only and links no alsa-lib. |
| USB gadget audio | 1 | Device side of the link. N/A. |
| sctp | 5 | False positives: the keyword "ASoC" matched "association". |

**The five ALSA-core records:**

- **CVE-2026-80716** (`pcm`: linked drain waiters on unlink) — needs `SNDRV_PCM_IOCTL_LINK` /
  `UNLINK`; vani never links streams. Not reachable.
- **CVE-2026-89979** (`pcm`: non-atomic ops vs trigger-start race) — needs PREPARE or
  HW_PARAMS on one thread racing START on another, on the same substream. Every vani path
  drives a handle from one thread. Not reachable in-tree; a consumer sharing one handle across
  threads could reach it, and the fix is kernel-side.
- **CVE-2026-98116** (`pcm`: mmap vs buffer reallocation, page UAF, local privilege
  escalation) — needs `mmap` of the PCM; vani uses `RW_INTERLEAVED` and never maps. Not
  reachable through vani, but any process with PCM access can reach it: **a host kernel
  update matter.**
- **CVE-2026-90198** (`core`: UAF in `snd_card_do_free()` when a devres-managed card is unbound
  while an fd is open, triggered by the final close) — **reachable**: a consumer holding a
  vani handle through a USB unplug or driver unbind, then closing it, closes exactly that fd.
  The close cannot be avoided (it is what `vani_close` must do), so there is no vani-side
  mitigation; kernel fix only.
- **CVE-2026-90060** (`control`: invalid kcontrols in the LED layer) — needs a write-only user
  element created with `ELEM_ADD`; vani never adds elements. Not reachable.

**Control writes in codec drivers** — CVE-2026-80526 (tas2562 volume put unvalidated),
CVE-2026-80583 / -80910 (lpass enum accessed as integer), CVE-2026-90068 (DAPM enum
off-by-one). vani's mixer writes only INTEGER and BOOLEAN elements, rejects ENUMERATED after
`ELEM_INFO`, and computes every volume as `min + (max - min) * percent / 100` with `percent`
checked to 0-100, so it never writes outside the range the element itself reports. None
reachable through vani.

**Against the new code**: nothing in the window touches `snd_pcm_open`'s busy path,
`O_NONBLOCK` handling, or the PREPARE-time flag copy 1.2.6 relies on.

**PulseAudio / PipeWire**: N/A by construction — vani is ioctl-only. Recorded rather than
skipped.

## 7. What remains

- **Capture half of `vani_busy_open` on hardware** — needs an ACL on `pcmC1D0c`. The kernel
  path is the one playback exercises, and the CPU suite covers the capture direction of the
  helper, but it has not run on a real capture node.
- **L-2 (open) — PCM and control descriptors are opened without `O_CLOEXEC`**, as they have
  been since v0.1.0. A consumer that forks and execs leaks the descriptor into the child,
  which then keeps the PCM busy after the parent closes its handle. Since 1.2.6 the parent's
  reopen fails at once instead of hanging, but the device stays unavailable until the child
  exits. Not changed here — it alters what a child inherits, which deserves its own decision.
  Filed in the roadmap (P2).
- Host kernels should take the fixes for CVE-2026-98116 and CVE-2026-90198 (§4). Neither has a
  vani-side mitigation.
