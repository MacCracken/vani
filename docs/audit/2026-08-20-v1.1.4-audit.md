# Vani v1.1.4 — Security & Toolchain Audit

**Date**: 2026-08-20
**Version audited**: 1.1.4 (patch — cyrius pin `6.5.5` → `6.5.31`; zero semantic source change)
**Kernel baseline**: running kernel `7.1.8-arch1-3`
**Prior audit**: [`2026-07-19-v1.1.2-audit.md`](2026-07-19-v1.1.2-audit.md)
**Audit gap closed**: 1.1.3 (pin `6.4.67` → `6.5.5`, 2026-08-02) shipped **without**
an audit doc, contrary to the P(-1) rule that even a clean sweep files one. This
sweep therefore covers the combined `6.4.67 → 6.5.31` distance for anything
that could reach vani, with the `6.5.6 → 6.5.31` window read line by line.
**Scope**: toolchain + stdlib dependency delta, syscall ABI diff, yukti/patra
API diff, ALSA UAPI ABI re-pin, external CVE sweep, CI/release gate audit.
Method: seven parallel analysis lenses, each non-INFO finding adversarially
re-derived by an independent verifier against live source; the load-bearing
results re-measured by hand (see *Reproduction*).

## Toolchain provenance — read this first

A **6.5.32** toolchain was installed on the dev box partway through this
release and repointed `~/.cyrius/{bin,lib,current}` at itself. Every number in
this document was therefore re-measured under a private `CYRIUS_HOME` whose
`bin`/`lib` symlink to `versions/6.5.31/` explicitly:

```bash
CH=/path/to/ch31
ln -sfn ~/.cyrius/versions          $CH/versions
ln -sfn ~/.cyrius/versions/6.5.31/bin $CH/bin
ln -sfn ~/.cyrius/versions/6.5.31/lib $CH/lib
echo 6.5.31 > $CH/current
CYRIUS_HOME=$CH PATH=$CH/bin:$PATH cyrius <cmd>          # no drift warning
```

Note also that `~/.cyrius/versions/6.5.31/bin/cycc` had itself been overwritten
at 08:47 by a locally-built binary; it self-reports `6.5.31` and was A/B'd
against 6.5.32 below, but a release cut from a clean checkout should install
the published 6.5.31 tarball, which is what CI does.

**Incidental result:** cycc 6.5.31 and 6.5.32 emit a **byte-identical**
`vani_smoke` (506,816 B) against the same stdlib, so the accidental exposure
changed nothing observable.

## 1. Binary-size attribution — a clean 2×2

`(cycc version) × (pinned stdlib snapshot)`, each axis varied independently via
hybrid `CYRIUS_HOME` prefixes, `CYRIUS_DCE=1`, x86_64:

| cycc | stdlib | `vani_smoke` | md5 |
|---|---|---|---|
| 6.5.5 | 6.5.5 | 472,712 B | `7c3d9e9b75e4…` |
| 6.5.5 | 6.5.31 | 502,720 B | `b2ad4ad5368a…` |
| 6.5.31 | 6.5.5 | 476,808 B | `2dfa1f19f028…` |
| 6.5.31 | 6.5.31 | 506,816 B | `34d5111808d3…` |

The axes are **perfectly orthogonal and exactly additive**: the stdlib snapshot
contributes **+30,008 B** under either compiler, and the compiler contributes
**+4,096 B** under either stdlib. Nominal 1.1.3 → nominal 1.1.4 is +34,104 B.

Unlike the 1.1.2 window — where cycc version had *zero* effect on vani's
emitted bytes — this window moves them, but only slightly. Segment-level:

| | R+E LOAD | RW LOAD |
|---|---|---|
| cycc 6.5.5 (stdlib 6.5.31) | `0x064d00` | `0x015a60` / `0x016a60` |
| cycc 6.5.31 (stdlib 6.5.31) | `0x065ce0` | `0x015a60` / `0x016a60` |

**+4,064 B of real text/rodata**, rounded up to one 4 KiB page in the file; the
RW segment is byte-identical and the reachable-function count is unchanged at
1307. This is codegen density, not new code.

### Where the +30,008 B went

Attributed by rebuilding one scratch tree against four `CYRIUS_HOME`s differing
only in which sub-library is rolled back (reproduced by hand for this document):

| Rolled back | `vani_smoke` | attributable |
|---|---|---|
| (none — all new) | 506,816 B | — |
| patra 1.13.9 → 1.12.12 | 494,464 B | **+12,352** |
| yukti 2.3.8 → 2.3.2 | 501,896 B | **+4,920** |
| sakshi 2.4.11 → 2.4.7 | 506,736 B | **+80** |
| all three | 489,440 B | +17,376 |

**patra alone is 41 % of the growth, and it is 100 % dead code for vani** (see
finding L-7). The residual ~+12,632 B is core stdlib: `alloc` 29,100 → 42,247 B,
`freelist` 5,967 → 26,448 B, `io` 24,707 → 32,082 B, `fs` 13,370 → 25,553 B on
disk. No vani function moved dead → live.

Other targets: aarch64 677,336 → 744,232 B; agnos 451,584 → 489,624 B.

> **Methodology note (carried forward from the 1.1.2 audit, re-confirmed here).**
> `cyrius build` resolves `include "lib/…"` from `$CYRIUS_HOME/versions/$PIN/lib`,
> **not** from the repo's gitignored `./lib/`. 1.1.2 proved this with a canary
> function; this sweep used a harsher test — appending a deliberate **syntax
> error** to `./lib/tagged.cyr` and rebuilding, which **succeeded**,
> byte-identical. `./lib/` is consulted only to emit the `./lib/ shadows
> version-pinned …` warning. Any A/B that swaps `./lib/` contents therefore
> measures nothing; the matrix above varies the **pin**. This fact is now
> promoted into [`docs/development/state.md`](../development/state.md) rather
> than living only in an audit appendix.

## 3. CI / release gates

Two defects, both introduced by tool-behavior drift rather than by vani.

### 3.1 The format gate was silently inverted — **fixed**

`.github/workflows/ci.yml` ran:

```bash
diff -q <(cyrius fmt "$f" 2>/dev/null) "$f"
```

That was correct through 1.1.3, when `cyrius fmt <file>` printed the formatted
source to stdout. Somewhere in the `6.5.6 → 6.5.31` window it changed to format
**in place** and print nothing. Consequences, both confirmed by running it:

1. The gate compares an **empty stream** against every file → fails for all 20
   gated files, unconditionally. A guaranteed red that says nothing about drift.
2. On a writable checkout it **silently rewrites sources**. It rewrote six of
   vani's during this investigation.

Replaced with `cyrius fmt "$f" --check`, which exits 0 clean / 1 on drift and
writes nothing. Validated both directions: exit 1 on a deliberately mis-indented
copy of `src/buffer.cyr`, exit 0 on the real one.

**Do not substitute the bare `cyrfmt --check` binary.** It reported CLEAN on the
same six files `cyrius fmt --check` correctly flagged as drifted — it is the
weaker check, and CI must not use it.

### 3.2 Untracked lint deferrals were unGated — **fixed**

cyrlint reports a `deferral` class (a TODO/follow-up comment with no
cross-reference) and **exits 0** on it, so CI's `^\s*warn ` gate never saw it.
vani carried one: a sentence in `src/alsa.cyr` claiming the `xferi[16]` →
`xferi[24]` correction was "filed as audit follow-up for the next P(-1) sweep".
That sweep ran and closed it at **0.3.0** (`docs/audit/2026-04-30-audit.md`,
HIGH finding). Comment now cross-references the audit and the 0.3.0 entry;
the CI lint gate now fails on `N untracked deferrals` as well as warnings.

This is **cleanup, not toolchain-forced**: cyrlint's output on vani's sources is
byte-identical between 6.5.5 and 6.5.31 (2 `sys_open` notes, 1 deferral, 0
warnings under both), so the bump adds no new lint surface.

### 3.3 Not closed

`cyrius_api_surface --scope=project` reports `108 public fns, surface matches
snapshot exactly`, but **CI never runs it** — the API-freeze guarantee that
1.0.0 established is currently enforced only by hand. Filed, not fixed here.

## 8. Findings

Severity per CLAUDE.md: **CRITICAL** (remote / privilege escalation), **HIGH**
(moderate effort), **MEDIUM** (specific conditions), **LOW** (defense-in-depth).

> **Confidence note — read before acting.** The analysis fan-out was cut short
> (see *Method and its limits*), so the adversarial verify pass did **not** run.
> Findings below are marked ✅ where they were independently re-derived by hand
> against live source or by re-running the measurement, and ⚠️ where they rest on
> a single unverified pass. Nothing marked ⚠️ should be actioned without
> re-checking it first.

### H-1 ✅ `enum AlsaHwParam` interval indices diverge from kernel UAPI by +2

**HIGH · no wire impact today · independently verified**

`src/alsa.cyr:156-169` numbers all 14 interval-group params two above the UAPI:
`SAMPLE_BITS`/`FIRST_INTERVAL` 10 (kernel 8), `CHANNELS` 12 (kernel 10), `RATE`
13 (kernel 11), … `TICK_TIME`/`LAST_INTERVAL` 21 (kernel 19). The mask group
(`ACCESS`=0, `FORMAT`=1, `SUBFORMAT`=2, `FIRST_MASK`=0, `LAST_MASK`=2) is
correct. The comment block at `src/alsa.cyr:67` describes these as "from Linux
UAPI sound/asound.h" — so the block is self-describing as a mirror of a spec it
does not mirror.

**Why nothing is broken today**, verified by reading every use site: all 12
interval references compute the *difference* `PARAM - SNDRV_PCM_HW_PARAM_FIRST_INTERVAL`
(`src/alsa.cyr:597,600,605,610,735,738`; `src/device.cyr:353-354`;
`programs/caps.cyr:93-96`), and `12-10 == 10-8`, so every array slot resolves
correctly. The only absolute uses are the mask params 0/1/2, which are right.
`rmask` is written all-ones at `src/alsa.cyr:230`, so no per-param bit is ever
computed from these numbers, and `HWP_CMASK_OFF` is defined but never read.

**The latent risk is one commit away.** A partial `HW_REFINE` that sets `rmask`
selectively as `1 << PARAM`, or any code decoding `cmask` to report which params
the kernel narrowed, would silently address bit 13 instead of bit 11 for `RATE`.

**Not fixed in 1.1.4** — see *Deferred* for the reasoning and the plan.

### H-2 ⚠️ `enum AlsaHwParam` has zero regression assertions

**MEDIUM** — the reason H-1 survived four audits. All 17 members are absent from
`tests/tcyr/vani.tcyr` except `SNDRV_PCM_HW_PARAM_FORMAT`, which appears only as
a call argument and is never compared to a literal.
`tests/tcyr/vani.tcyr:348-361` pins the *struct offsets* but not one param index.
The 1.1.2 audit's "18 ioctls + 8 struct sizes" scope never included this enum.

### H-3 ⚠️ 45 of 125 pinned enum members have no regression assertion

**MEDIUM.** The operationally risky ones: `AlsaCtlElemListLayout` (its `PIDS`=16
offset is where `src/mixer.cyr:334` writes a userspace heap pointer for the
kernel to fill — a wrong offset hands the kernel a pointer assembled from
adjacent u32 fields) and `AlsaAccess` (`RW_INTERLEAVED`=3 is written into the
ACCESS mask on every open; a wrong value selects an mmap mode vani has no code
path for). All values are correct today. `SNDRV_PCM_IOCTL_RESET` is additionally
dead — no call site anywhere — so it should be asserted or dropped.

### H-4 ⚠️ No test pins the nr byte or direction bits of 16 of the 18 ioctls

**MEDIUM.** `tests/tcyr/vani.tcyr:368-385` asserts only the size bits and
`:387-395`/`:452-458` only the type byte. Full 32-bit equality is asserted for
exactly two constants (`RESUME` at `:577`, `PAUSE` at `:587`). Concretely:
`HW_PARAMS` (0xC2604111) and `HW_REFINE` (0xC2604110) differ only in the nr
byte, as do `DROP`/`DRAIN` — swapping either pair leaves every current assertion
green. So does an `_IOR`/`_IOW` direction flip on `WRITEI`/`READI`, which would
make the kernel copy the wrong direction on a 24-byte struct. The fix is
strictly *less* code: full 32-bit equality for all 18, the shape already used
for `PAUSE` and `RESUME`.

### L-1 ⚠️ Two stale struct-size comments contradict the (correct) pinned constants

**LOW.** `src/alsa.cyr:912` says "snd_pcm_status is 192 bytes" and `:922`
allocates `var status[192]`; the real size is 152, which the STATUS ioctl
correctly encodes and the suite correctly asserts. (Carried from 1.1.2 audit
INFO #3, filed for 1.2.0 — still open, and the 1.1.4 fmt reflow moved its line
citations by +2.) Separately `src/alsa.cyr:302-303` describes
`snd_ctl_elem_list` as 280 B; it is 80, which the enum and the ioctl both use
correctly. Both are over-allocations or comments, not overflows — the hazard is
a future editor trusting the comment and baking a wrong size into a new ioctl,
which is exactly the ENOTTY failure mode the surrounding block warns about.

### L-2 ⚠️ `audio_get_state` reads the 4-byte `snd_pcm_status.state` field with `load64`

**LOW.** `src/alsa.cyr:926` returns `load64(&status)` against a 4-byte field.
Benign on little-endian because the adjacent bytes are within the
over-allocated 192-byte buffer and the high word reads as the next field, but it
is a type mismatch on a kernel-filled struct.

### L-3 ⚠️ Unchecked `alloc()` return in `vani_ring_new` — **pre-existing**

**LOW, not bump-related.** `src/buffer.cyr:47-48`:
`var rb = alloc(40); store64(rb, alloc(sz));` — `rb` is stored into with no NULL
check, so total heap exhaustion (alloc's sentinel is 0) yields a write to
address 0. Byte-identical to 1.1.3.

### L-4 ⚠️ Unbounded kernel-supplied element count in `vani_mixer_list_elements` — **pre-existing**

**LOW, not bump-related.** `src/mixer.cyr:317-329` reads `count` straight from
the ELEM_LIST ioctl with no upper bound, computes `cap = count * 64`, then
`alloc(cap); memset(pids, 0, cap)`. A count above ~33.5 M makes `cap` exceed
`ALLOC_MAX` (2 GiB), `alloc` returns 0, and `memset` writes from address 0.
Requires a hostile or broken ALSA driver. CLAUDE.md's "do not trust external
data (kernel ioctl returns…) without validation" applies directly. Byte-identical
to 1.1.3.

### L-5 ⚠️ Windows peer newly defines `SYS_IOCTL = 16`

**LOW, informational.** `lib/syscalls_windows.cyr:51` now declares `SYS_IOCTL`,
where the 6.5.5 tree had none. All 20 raw `syscall(SYS_IOCTL, …)` sites would
now *compile* for a PE target and return −38/−ENOSYS at runtime, where
previously the build failed loudly. Fail-safe, not fail-wrong — vani's callers
check `r < 0`. No effect on x86_64-linux / aarch64-linux / agnos, vani's only
targets. Worth an explicit statement somewhere that a PE build of vani is *not*
a supported configuration, so nobody reads a clean Windows compile as a working
audio path.

### L-6 ✅ The three lint `raw sys_open` notes are FALSE POSITIVES — adoption declined

**LOW.** cyrlint suggests `io.cyr`'s `xopen`/`file_open` at `src/alsa.cyr:481`,
`:501` and `src/mixer.cyr:97`. All three are already inside
`#ifdef CYRIUS_TARGET_AGNOS` arms that never reach `sys_open` (agnos returns via
`sys_snd_open()`, returns 0, and fails closed respectively); the linter
pattern-matches the text without seeing the enclosing `#ifdef`. Adoption would
also be a functional no-op (`file_open` *is* `sys_open(path, flags, mode)` on
every non-agnos target) and `xopen` is not a drop-in — it hardcodes mode 0644
where vani passes 0. **Decisive cost:** `src/alsa.cyr` is the sole module of
`dist/vani-core.cyr`, whose sidecar is 4 leaves; `lib/io.cyr` requires
`syscalls` + `result`, so adopting it there would push `dist/vani-core.deps` to
6, working directly against the core profile's minimal-footprint purpose.
**Declined**, deliberately, and recorded here so the next sweep does not
re-litigate it.

### L-7 ✅ patra is 41 % of the binary growth and 100 % dead code

**LOW, size only.** See §1 for the reproduced attribution. patra reaches vani
only through yukti's `device_db`, which vani never enters; DCE NOPs the bodies
but the rodata survives (`strings` finds `PTRAH`, `patra: invalid magic` in both
the x86_64 and agnos binaries — which incidentally qualifies CLAUDE.md's "agnos
gates it off": yukti's `device_db` module is gated, but `lib/patra.cyr` is still
compiled in, at both pins, so pre-existing). Now also in `dist/vani.deps`, so
downstream consumers inherit it. Upstream item for yukti, not a vani defect.

## 9. External CVE / 0-day sweep

**Window** 2026-07-19 (prior sweep) → 2026-08-20. **Host kernel** 7.1.8-arch1-3.
Method: NVD 2.0 API across ALSA / snd_pcm / sound-usb / sound-core / hda /
hw_params / USB-audio keywords for the window, every cited record fetched
directly; upstream `torvalds/master` `include/uapi/sound/asound.h` fetched and
diffed against the host header; GitHub Security Advisories API queried for
`MacCracken/cyrius`.

**Result: 19 new in-window Linux kernel audio CVEs. Zero are triggerable through
vani's own ioctl surface.** The 2026-07-19 batch (CVE-2026-64001 / -64029 /
-64133 / -64134) was already dispositioned by the prior audit; genuinely new
content starts 2026-07-25.

**Closest approach — CVE-2026-74498** (published 2026-08-15, `sound/usb/endpoint.c`).
When a USB audio endpoint sets the `fill_max` descriptor flag,
`data_ep_set_params()` promotes `curpacksize` to `maxpacksize` while `maxsize`
stays at the sample-rate-derived value, so the DMA buffer
(`maxsize * packets`) is too small and the host controller writes past it,
corrupting kernel heap. This runs inside `snd_usb_hw_params` — i.e. *directly
beneath* vani's `SNDRV_PCM_IOCTL_HW_PARAMS` call and the subsequent WRITEI
stream. vani is the victim, not the attacker, and **has no mitigation available**:
`fill_max` lives in the USB endpoint descriptor, entirely below the ALSA UAPI
boundary, and `AUDIO_FRAMES_MAX` caps frame counts, not per-packet sizes.
Fixed in 5.10.265, 5.15.216, 6.1.183, 6.6.151, 6.12.103, 6.18.44, **7.1.8**, 7.2.
The host is exactly at 7.1.8 — **verified patched, with zero margin.**
*Downstream implication: anything below 7.1.8 on the 7.1 line is exposed when
opening USB audio through vani.* No vani-side fix exists to write.

**CVE-2026-64490** (`sound/virtio/virtio_kctl.c`, CVSS 8.4) — virtio-snd trusts
device-supplied control type and value count, giving OOB access in
`virtsnd_kctl_info/get/put`. Reached beneath ioctls vani *does* issue
(`ELEM_INFO` `src/mixer.cyr:126`, `ELEM_READ` `:201`/`:257`, `ELEM_WRITE`
`:171`/`:243`) in a guest whose audio is virtio-snd behind a hostile vhost-user
daemon. Patched on host (7.1.4). vani's element-type gates
(`src/mixer.cyr:151`/`:188`/`:227`) are already the right defense-in-depth, but a
type check *after* the ioctl cannot prevent an OOB *during* it. Noted because
prior sweeps only considered physical cards — **virtio-snd is a new attack
surface class for the mixer path.**

**Unreachable:** CVE-2026-68200 / -68201 (ALSA timer UAF pair — vani opens no
timer or sequencer node); the 2026-07-25 driver-probe batch of 12 (outside
vani's surface by the yukti-owns-discovery boundary); CVE-2026-74295 / -64478 /
-64601 / -68346 / -64584 (hotplug, ASoC DAPM, gadget paths).

**Forward drift watch.** Upstream bumped `SNDRV_CTL_VERSION` 2.0.9 → 2.0.10 and
added `SNDRV_CTL_IOCTL_CARD_BYTES _IOWR('U', 0x02, …)`. Purely additive at a
number vani does not use; all four CTL structs are textually identical between
host header and upstream master, and `snd_ctl_card_info` keeps its 376-byte ABI,
so none of vani's five `src/mixer.cyr:33-37` constants shift. One semantic
change to remember: `snd_ctl_card_info.components` may now carry a `>` truncation
marker, with the full string available via the new ioctl. vani never issues
CARD_INFO, so this is a watch item only — **do not** pin the new constant now;
an unused pinned constant is exactly the rot the PAUSE encoding suffered before
v1.0.0.

**Cyrius toolchain:** zero public advisories, as expected for a first-party
project. The 6.5.5 → 6.5.31 delta cannot be gated by CVE feeds — the toolchain
diff analysis in §1-§3 is what stands in for it.

## Method and its limits

Seven parallel analysis lenses were launched: toolchain-delta, syscall-ABI,
yukti/patra API, core-stdlib diff, UAPI re-pin, CVE sweep, CI gates. **Five
completed. The run was then stopped deliberately** because the CI-gates lens ran
`git stash` / `git checkout` inside the working tree and reverted the release in
progress — an instruction violation, the tree was restored from a snapshot and
every gate re-run from scratch under the pinned 6.5.31 toolchain. Consequences
for this document, stated plainly:

- **The adversarial verify pass never ran.** Findings are marked ✅ / ⚠️ above
  accordingly. The ✅ ones were re-derived by hand for this document.
- **The toolchain-delta lens (the line-by-line read of the 3,230-line cyrius
  6.5.6-6.5.31 changelog) did not complete.** Its ground is partly covered by
  the syscall-ABI and core-stdlib lenses plus the byte-level 2×2, but this
  audit does **not** claim an exhaustive reading of that changelog.
- The CI-gates lens's *conclusions* are not relied on here; §3 was re-derived
  by hand, and its one useful artifact — an end-to-end 1.1.4 release-workflow
  dry run — is what made the tree recoverable.

Corrections the lenses made to working assumptions, all already folded into the
CHANGELOG and `state.md`: the src churn is **not** whitespace-only (there is the
one comment rewrite); the 15 agnos yukti warnings were **already zero at 6.5.5**,
so this bump did not fix them; and the lenses' own measurements ran on cycc
6.5.32 rather than the pinned 6.5.31 — every number in this document was
re-measured on 6.5.31, and the two compilers were shown to emit an identical
binary anyway.
